Guía completa del proyecto

Cómo funciona el flujo LightSpec y por qué ordena mejor el trabajo

Este proyecto define un flujo estructurado para trabajar con backlog, exploración, especificaciones, memoria operativa y ejecución usando skills especializadas. La idea central es evitar trabajo improvisado, reducir ambigüedad y obligar a que cada cambio deje evidencia clara en artefactos del proyecto.

En lugar de saltar directo a implementar, el sistema puede iniciar un proyecto, adaptar uno existente, explorar ideas, registrar features, crear especificaciones, implementar, sincronizar documentación o validar estándares. Eso hace que el proceso sea más auditable, más barato de operar y más fácil de retomar.

Qué resuelve
9 skills activas del flujo
4 tipos clave de artefactos
1 fuente formal de backlog
0 saltos de flujo deseados

Resultado esperado

Un proyecto donde cada feature tiene un estado claro, cada decisión importante deja rastro, y cada skill sabe cuándo puede ejecutarse y qué debe producir antes de pasar a la siguiente etapa.

Qué hace este sistema

LightSpec organiza el trabajo alrededor de artefactos persistentes. El flujo no solo decide qué hacer, sino qué documento o archivo debe quedar actualizado después de cada paso y cuándo conviene pensar antes de formalizar.

Backlog

Controla el estado formal

feature_list.json es la fuente de verdad para features, estados, aceptación, uso de SDD y orden del trabajo.

Exploración

Refina ideas antes de escribir

explore-ideas permite hacer lluvia de ideas, cuestionar supuestos y aterrizar necesidades en features candidatas sin tocar artefactos.

Ejecución

Convierte intención en cambio trazable

specs/ y memory/ conectan especificación, implementación y seguimiento para que el trabajo pueda retomarse sin ambigüedad.

Beneficios principales

El valor del flujo no está solo en ordenar archivos, sino en reducir costo de coordinación, ambigüedad y retrabajo durante el desarrollo.

Más claridad operativa

Cada skill tiene prerequisitos, límites y resultados concretos. Eso facilita saber cuándo avanzar y cuándo detenerse.

Mejor descubrimiento

La exploración previa evita convertir ideas vagas en backlog débil. Primero se piensa, luego se formaliza.

Menor costo en tokens

Al separar tareas por skill, se puede usar un modelo barato para intake o backlog y reservar modelos más potentes para especificación o código.

Diagrama del flujo

El flujo tiene dos entradas posibles: iniciar un proyecto desde cero o adaptar uno ya existente. A partir de ahí, la exploración y el backlog controlan el resto del proceso.

Lectura del diagrama

El flujo avanza desde preparación hacia exploración, backlog, especificación, implementación y sincronización. No todas las rutas pasan por todas las skills: algunas son obligatorias solo cuando la idea todavía es difusa, cuando una feature usa SDD o cuando existe deriva documental.

Entrada Núcleo Revisión Ruta condicional
1 · Entrada

Init Project o Adapt Old Project

El flujo comienza creando un proyecto nuevo o adaptando uno existente al sistema de backlog, specs y memoria.

  • Init Project crea estructura base y feature_list.json.
  • Adapt Old Project inspecciona código real, clasifica capacidades y crea artefactos faltantes.
Resultado El workspace queda preparado con backlog inicial o backlog adaptado, más reglas y estructura coherente.
→
2 · Exploración

Explore Ideas

Cuando una necesidad todavía es difusa, esta skill abre una conversación de descubrimiento antes de tocar el backlog.

  • Cuestiona supuestos y compara alternativas.
  • Puede leer código para aterrizar la idea en la realidad del proyecto.
Resultado Una idea refinada y una lista de features candidatas listas para aprobación posterior.
→
3 · Backlog

Add Feature y Validate Feature List

Aquí se registran necesidades, se detectan duplicados, se divide una solicitud compuesta y se ordena el backlog.

  • Add Feature agrega, reabre o divide features con aprobación.
  • Validate Feature List revisa conflictos, huecos y prioridad.
Resultado Un backlog consistente, priorizado y con aceptación verificable para cada feature relevante.
→
4 · Especificación y ejecución

Create Spec e Implement Feature

Si una feature usa SDD, primero pasa por spec. Luego la implementación trabaja una sola feature a la vez.

  • Create Spec mueve la feature a spec_ready cuando queda completa.
  • Implement Feature valida y cierra en done solo si las pruebas pasan.
Resultado Cambio implementado con especificación cuando corresponde, memoria actualizada y trazabilidad completa.
5 · Revisión

Validate Standards

Revisa el código contra constitution.md y code_standards.md sin modificar archivos.

Resultado Informe de alineación, riesgos y desviaciones comprobables frente a los estándares.
↔
6 · Documentación

Sync Docs

Detecta deriva entre código y artefactos formales. Si encuentra capacidades no formalizadas, enruta a la secuencia correcta: Explore Ideas → Add Feature → Validate Feature List → Create Spec cuando aplique.

Resultado Backlog, specs y memoria sincronizados con la realidad del repositorio sin tocar el código fuente.

Artefactos que sostienen el sistema

El flujo funciona porque cada skill produce o consume archivos concretos. Eso reduce ambigüedad y hace posible retomar trabajo sin reconstruir contexto desde cero.

feature_list.json

Es la fuente formal de estado. Guarda features, aceptación, uso de SDD, estados y reglas del proyecto.

  • Lo crean o adaptan: Init Project y Adapt Old Project.
  • Lo actualizan: Add Feature, Create Spec, Implement Feature y Validate Feature List.

memory/

Mantiene memoria operativa y memoria estable por feature para que la ejecución no dependa solo del chat actual.

  • current.md guarda el trabajo en curso.
  • history.md resume avances cerrados.
  • Los archivos por feature conservan decisiones y contexto duradero.

specs/<feature>/

Contiene requirements.md, design.md y tasks.md cuando una feature requiere SDD.

  • Se crea o actualiza en Create Spec.
  • Se consume en Implement Feature.

constitution.md, code_standards.md y workflow_rules.md

Definen principios, límites y criterios verificables. Son el marco común del flujo después del inicio.

  • Se usan para revisión, exploración, especificación e implementación.
  • Evitan que cada skill invente reglas locales incompatibles.

Principios que hacen funcionar el flujo

Estos principios aparecen repetidamente en el proyecto porque son los que mantienen el sistema ordenado, trazable y relativamente barato de operar.

Una fuente formal de verdad

El backlog manda sobre el estado de las features. La memoria ayuda, pero no reemplaza el estado formal.

Pensar antes de escribir

No toda idea debe entrar directo al backlog. La exploración sirve para validar si hay una feature real y cómo debería delimitarse.

Aprobación humana explícita

No se escriben cambios materiales de backlog, specs o documentación sin aprobación previa cuando el flujo lo exige.

Una línea de trabajo cada vez

El sistema evita abrir demasiados frentes paralelos. Eso mejora consistencia y reduce ruido contextual.

Recomendaciones de modelos por skill

La lógica general para ahorrar tokens es simple: usar modelos baratos para intake, exploración, backlog y documentación; reservar modelos más potentes para síntesis amplia, especificación técnica e implementación real.

Referencia de costo usada para estas sugerencias: la tabla de modelos y pricing de GitHub Copilot. En esa tabla, GPT-5 mini y Claude Haiku 4.5 son opciones económicas; GPT-5.4 mini y Claude Sonnet 4.x son el punto medio; GPT-5.3-Codex y variantes más grandes tienen sentido cuando el trabajo es claramente de implementación profunda.

Init Project

Intake estructurado, reglas base y generación inicial de artefactos.

Anthropic · Claude Haiku 4.5

Conviene por costo bajo y rapidez para formular preguntas y preparar el punto de partida.

OpenAI · GPT-5 mini

Buen equilibrio entre precio y precisión para inicialización y confirmaciones.

Adapt Old Project

Lectura amplia del repositorio, síntesis de capacidades y adaptación retroactiva.

Anthropic · Claude Sonnet 4.6

Más adecuado para síntesis de repositorios y agrupación de capacidades sin pagar el costo de Opus.

OpenAI · GPT-5.4

Mejor opción del grupo para análisis amplio, ordenamiento de evidencia y definición de backlog retrospectivo.

Explore Ideas

Conversación exploratoria, comparación de caminos y refinamiento antes del backlog.

Anthropic · Claude Sonnet 4

Muy útil para conversaciones abiertas, contraste de opciones y preguntas de descubrimiento con buen costo.

OpenAI · GPT-5.4 mini

Buen punto medio para explorar ideas, leer código cuando haga falta y aterrizar propuestas en features claras.

Add Feature

Edición de backlog, splits, aceptación y confirmación de SDD.

Anthropic · Claude Haiku 4.5

Ideal para decisiones de backlog relativamente acotadas, con buen costo para preguntas y redacción estructurada.

OpenAI · GPT-5 mini

Muy conveniente para detección de duplicados, creación de nombres y propuestas ligeras de aceptación.

Create Spec

Requisitos, diseño, tareas y consistencia entre documentos.

Anthropic · Claude Sonnet 4.5

Buen punto medio para transformar una feature en documentación técnica coherente y trazable.

OpenAI · GPT-5.4 mini

Más barato que GPT-5.4 completo y suficientemente fuerte para requisitos, diseño y checklist ejecutable.

Implement Feature

Código, validación, pruebas y cierre de la feature.

Anthropic · Claude Sonnet 4.6

Buena opción para implementación iterativa y depuración manteniendo costo controlado.

OpenAI · GPT-5.3-Codex

Es la recomendación más fuerte para trabajo puramente de código, cambios multiarchivo y ciclo de pruebas.

Sync Docs

Comparación entre implementación real y artefactos documentales.

Anthropic · Claude Sonnet 4

La tarea requiere más matiz que Haiku para detectar deriva y proponer la secuencia correcta de formalización.

OpenAI · GPT-5.4 mini

Equilibrio correcto para contraste entre código, backlog y specs sin subir al costo de los modelos mayores.

Validate Feature List

Revisión de huecos, conflictos, prioridades e incrementos del backlog.

Anthropic · Claude Sonnet 4

Encaja bien para modelado de backlog y priorización cuando ya no basta una revisión muy barata.

OpenAI · GPT-5.4 mini

Conviene por costo moderado y buena capacidad para ordenar dependencias y detectar inconsistencias.

Validate Standards

Auditoría basada en evidencia contra constitution y code standards.

Anthropic · Claude Sonnet 4.5

Revisión adecuada para separar hallazgos confirmados de advertencias y sostener un análisis técnico argumentado.

OpenAI · GPT-5.4 mini

Buena relación costo-utilidad para comparar criterios contra código sin necesidad de un modelo extremo.

Recomendaciones prácticas para usar el flujo mejor

Estas recomendaciones ayudan a que el sistema no solo se vea ordenado en papel, sino que realmente funcione bien en sesiones largas de GitHub Copilot.

Usar modelos baratos por defecto

Para intake, exploración, backlog y documentación, empieza con Haiku 4.5 o GPT-5 mini. Escala solo cuando el problema sea claramente más complejo.

Explorar antes de formalizar

Cuando una idea sea ambigua o compuesta, conviene pasar primero por explore-ideas para no llenar el backlog con features débiles.

Tratar el backlog como contrato

Si el backlog está mal, todo lo demás se degrada. Conviene validar y corregir el backlog antes de abrir un ciclo largo de implementación.

No saltarse Sync Docs

Cuando el código evoluciona fuera del flujo, esta skill evita que el sistema termine con backlog y specs desconectados de la realidad.

Usar SDD solo donde aporte valor

No toda feature necesita spec formal. Conviene usar SDD cuando la complejidad, el riesgo o la coordinación justifican el costo extra de documentación.

Evaluar un orquestador en el futuro

El flujo actual ya parece un sistema orquestado. Un agente orquestador podría decidir la siguiente skill válida y reducir duplicación de lógica entre prompts.

Conclusión

Este proyecto no es solo una colección de prompts. Es una arquitectura de trabajo para convertir intención en exploración, exploración en backlog, backlog en especificación, especificación en implementación y código en documentación mantenible.

Su principal ventaja es que obliga a dejar evidencia en artefactos persistentes. Su principal desafío es mantener la disciplina del flujo. Cuando ambas cosas se equilibran, el resultado es un sistema mucho más trazable y eficiente para trabajar con GitHub Copilot.

Resumen ejecutivo

  • Entrada por Init Project o Adapt Old Project.
  • Exploración opcional y valiosa con Explore Ideas.
  • Backlog formal en feature_list.json.
  • SDD opcional, no automático.
  • Implementación una feature a la vez.
  • Sincronización documental y auditoría técnica cuando haga falta.
